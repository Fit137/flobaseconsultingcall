# Flobase GTM Walkthrough v2 — Build Prompt and Design Instructions

**This supersedes `walkthrough_deck_brief.md`.** That brief specified a linear 14-slide 3D deck with no design system, because at the time there was nothing to inherit. The reference deck changes that: it is a working, comparable artifact with a complete design system, so v2 forks it rather than inventing anything.

**What the reference is.** `index.html`, title *Health Plan Chat — Sprint 1 GTM Walkthrough v2*. Same genre of work: a GTM strategy for a health-tech product, eight dashboards, delivered as a self-contained hub application. It is not a slide deck. It is a **navigable app with two modes**, and that distinction is the single most important thing to carry over.

**How to use this document.** Part A is the paste-ready prompt. Parts B through D are the design instructions and content payload it refers to. Hand the builder all four parts plus `index.html`.

## Part A — The master prompt

> Build a self-contained GTM walkthrough application for **Flobase**, an operating system for US life insurance agencies. Attached is `index.html`, a working reference deck built for a comparable project. **Fork it.** Keep the architecture, the design system, the motion and the hero-object idiom; replace the content, the dashboards and two of the ten hero graphics.
>
> **Read the reference first, in this order:** the `:root` token block and its two dark-theme mirrors, the hero CSS block (the long comment beginning "Hero objects — one per summary slide"), the `GTM.SLIDES` builder, the `GTM.HERO` factory, and the boot module with `fit()`, `render()` and `handleKey()`. Everything you need is in there. Do not introduce a framework, a CDN, a font loader or a 3D library that the reference does not already use.
>
> **The architecture to preserve exactly:**
> - A fixed design canvas of 1400×800, absolutely positioned at 50%/50%, scaled by `Math.min(w/dw, h/dh, 1.7)` on resize. Never reflow the slide; scale it.
> - A collapsible left rail of slide thumbnails, each showing a two-digit number, kicker, title and stat. Rail state persists in `localStorage`.
> - Hash routing: `#/s/<n>` for slides, `#/d/<key>` and `#/d/<key>/t/<tab>` for dashboards.
> - A **dashboard viewer mode**: clicking "Open full dashboard" swaps to a full-bleed `iframe` whose `srcdoc` is generated by a `buildDoc(key, theme)` function and cached per key and theme. The iframe forwards keystrokes back to the shell via `postMessage`, and the shell pushes theme changes into it the same way. This two-mode structure is the reference's best idea. Keep it.
> - Light and dark theme, toggled in the top bar, persisted in `localStorage`, defaulting to `prefers-color-scheme`, and pushed into the iframe.
> - Keyboard: arrows, space, PageUp/PageDown, Home, End and number keys in hub mode; arrows to step dashboards and Escape to return in viewer mode.
>
> **The content is in Part C.** Ten dashboards instead of the reference's eight, so twelve slides: a cover, ten summary slides, a closing slide. Every figure in Part C traces to a source workbook in this repository; do not round, embellish or invent any of them, and preserve every `{TBD}` exactly as written, because each one marks something deliberately not yet claimed.
>
> **The one design decision I cannot make for you** is in Part D. The reference's accent green is another company's brand colour. Read Part D before you write a token.
>
> **Non-negotiables:**
> - Every hero object carries its slide's argument. If a graphic would still make sense on a different slide, it is wrong.
> - Every interactive element in a hero has `tabindex="0"` and a `:focus-visible` state identical to its `:hover` state. The presenter navigates by keyboard on stage.
> - Tabular figures on every numeral, everywhere, including inside tooltips.
> - The entire animation layer sits inside `@media (prefers-reduced-motion: no-preference)`, exactly as the reference does it. Reduced motion is then the resolved state for free, with no second code path.
> - Self-contained single file. No network requests at runtime.
>
> Build the shell and the cover first, then slide 02 and slide 09, which are the two that carry the deck. Get those three right and the rest follow the same patterns.

## Part B — Design instructions

Everything here is lifted from the reference unless marked **[NEW]** or **[CHANGED]**.

### B1 · Tokens

Take the reference's `:root` block verbatim, including both dark mirrors (the `prefers-color-scheme` media query guarded with `:root:not([data-theme="light"])`, and the explicit `:root[data-theme="dark"]`). That three-way pattern is what makes the toggle win in both directions.

The structural tokens carry over untouched:

```css
--canvas --surface --surface-alt --raised     /* four surface steps      */
--ink --slate --stone                          /* three foreground steps  */
--hairline                                     /* the only border         */
--band --band-fg --band-hair                   /* the inverted block      */
--shadow-1 --shadow-2 --shadow-3               /* three elevations        */
--dw:1400px --dh:800px                         /* the fixed canvas        */
```

**Per-slide accent triplet.** The reference's most transferable idea. Each hero, lane, card or marker sets three variables together and every rule inside reads from them:

```css
--acc      /* the line and fill colour        */
--acc-t    /* the same colour at 9-13% alpha  */
--acc-d    /* a dark companion for text       */
```

Text on an accent surface is never the raw accent. It is `color-mix(in oklab, var(--acc), var(--ink) 42%)`, which keeps every category colour legible in both themes without a second palette. Copy that formula exactly.

### B2 · Type

Figtree for everything, `Source Code Pro` for numerals, labels, eyebrows and tooltip metadata. Both are already embedded as `woff2` in the reference; reuse those faces rather than adding a loader.

The scale, verbatim:

`text-wrap: pretty` on every heading and every wrapping paragraph.

### B3 · The shell

```
  #rail          --surface-alt, hairline right border, scrolling .thumb list
  #pane

```

Two slide layouts only:

- **`.cover`** — `grid-template-rows: 1fr auto`. Top row is a two-column split of copy and `HERO_COVER`. Bottom row is `.launcher`, a hairline-topped strip holding a `repeat(4,1fr)` grid of `.lcard` dashboard links under `perspective:900px`. **[CHANGED]** ten dashboards, so run the card grid as two rows of five.
- **`.sum`** — `grid-template-columns: 1fr 1.02fr`, `gap:52px`, vertically centred. Left column in fixed order: `.numrow` (big accent number plus eyebrow), `h2`, `.statline`, `.blurb`, `.sowhat`, `.openbtn`, `.contents`. Right column is the hero.

`.sowhat` is the reference's sharpest component: an inverted block on `--band` with `--band-fg` text, 12px radius, holding a single sentence of consequence. It is the only inverted element on the slide and it should stay that way.

### B4 · Motion

One curve for content, `cubic-bezier(.22,1,.36,1)`. One curve for chrome, `cubic-bezier(.2,0,.2,1)`. Nothing else.

```css
@keyframes rise   { from{opacity:0;transform:translateY(10px)} to{opacity:1;transform:none} }
@keyframes hrise  { from{opacity:0;transform:translateY(14px)} to{opacity:1;transform:none} }
@keyframes hpop   { from{opacity:0;transform:scale(0)}         to{opacity:1;transform:scale(1)} }
@keyframes hsway  { 0%,100%{rotate:y 0deg} 50%{rotate:y -.9deg} }
```

| What | Timing |
|---|---|
| `.anim` copy elements | `rise` 460ms |
| Hero body | `hrise` 620ms |
| Hero legend | `hrise` 620ms, 260ms delay |
| Scatter dots | `hpop` 420ms, delay `calc(var(--i) * 26ms + 200ms)` |
| Lanes, marks, pills, cards | `hrise`/`hriseT` 520ms, delay `calc(var(--i) * 70ms + 140ms)` |
| **Ambient sway** | `hsway` **13s ease-in-out, 900ms delay, infinite** |
| Hover, all objects | 150–170ms |
| Hinge rotation | 420ms |

Two mechanics worth naming, because they are the reference's real craft:

**Entry replays on every visit.** Animations are scoped to `.slide[data-active="true"]`, so returning to a slide re-runs its build. A presenter who goes back to make a point gets the argument re-drawn rather than a static frame.

**`hsway` is the whole 3D feel.** A single `rotate: y` oscillation of **0.9 degrees** over 13 seconds, applied to the hero container. That is all. It reads as a solid object breathing on a table rather than a diagram, and it costs one keyframe. Do not increase the amplitude. Anything past about 1.5 degrees stops looking like weight and starts looking like a bug.

### B5 · The hover model

Every hover in the reference is the same four moves, and the consistency is why ten different objects feel like one system. Apply it to every new object too:

1. **Tint** — background becomes `var(--acc-t)`.
2. **Commit the edge** — `border-color` becomes `var(--acc)`, and the 3px left border it already carries reads as the object's spine.
3. **Coloured shadow** — `box-shadow: 0 14px 30px -14px var(--acc)`. The shadow takes the object's own accent, never neutral grey. This is what makes hover feel lit rather than raised.
4. **Displace slightly** — `translate: 3px 0` for a list item, `translateZ(26px)` for a stack pill, `scale: 1.55` for a scatter dot.

Reverse on leave at the same duration. `:focus-visible` produces the identical state, always, with `outline:none` on the object and the tooltip doing the work.

**Tooltips.** `.ht` marks the trigger, `.htip` is the panel: `--ink` background, `--canvas` text, 8px radius, `max-width:222px`, opacity plus a 3px lift over 150ms. Side variants `.te` and `.ts` flip the anchor when the trigger sits within 30% of an edge. Tooltip metadata is mono, accent coloured, tabular. Every tooltip works on focus as well as hover.

**Isolation, applied through `:has()`.** The hinge shows the pattern: hovering one face rotates it toward the viewer to `2deg` and pushes the other to `-38deg` at `0.45` opacity. Sibling suppression is what makes hover informative rather than decorative, and `:has()` does it in CSS with no JavaScript.

**Card tilt.** `.lcard` on the cover tracks the pointer at `rotateY(px*16deg) rotateX(-py*16deg) translateZ(6px)`, driven by a delegated `mousemove` on the canvas and gated on `prefers-reduced-motion`. Keep the gate.

### B6 · Reduced motion

The reference wraps its **entire** animation layer in `@media (prefers-reduced-motion: no-preference)` and adds one targeted `reduce` rule to kill a width transition. Copy this approach exactly. It means the resolved state is the default and animation is the enhancement, so there is no second code path to maintain and no risk of a reduced-motion user seeing a half-built graphic.

## Part D — Decisions before a token is written

**D1 · The accent colour is another company's brand.** `#00ED64` and `#001E2B` are Health Plan Chat's palette, and the category accents (`#00D2FF`, `#B55CF3`, `#EE3984`, `#006CFA`) come from their token file. The **structure** is generic and safe to fork: four surface steps, three foreground steps, one hairline, three shadows, the `--acc / --acc-t / --acc-d` triplet and the `color-mix` legibility rule. The **values** are not ours.

Three options, in the order I would take them:

1. **Substitute Flobase's brand colours into the same structure.** Correct, and needs someone to supply the hex values, since flobase.tech was not reachable from this environment and no codebase exists in the repository.
2. **Keep the structure and pick a neutral accent** that is demonstrably not the reference's, retaining the four category accents for quadrant coding only.
3. **Fork the palette wholesale.** Fastest, and I would not ship it. Two GTM decks in adjacent markets sharing a signal green is a real confusion risk.

Nothing else in Part B depends on which you choose.

**D2 · This reverses your earlier instruction, deliberately.** You previously asked me not to enforce design specs, because Claude Design carries its own system and a competing spec would conflict. Parts B and C are a full design specification, which is the opposite. That is correct now: you supplied a concrete reference and asked for it to be forked, so the reference *is* the system being inherited. Worth stating so the change is visible rather than silent.

**D3 · Ten dashboards will not fit the cover's four-column card grid.** Two rows of five is specified above. Five cards per row at the 1400px canvas width is tight but workable; if it crowds, drop `.lcard` padding from `13px 14px 14px` to `11px 12px 12px` before you touch the type scale.

**D4 · The reference's dashboards are hand-authored JS data, not converted spreadsheets.** Its `sheets` renderer reads structured arrays, so the ten Flobase dashboards need transcribing from the source markdown into that shape. That is the largest single piece of work in this build, and it is mechanical rather than creative. The `.xlsx` files in this repository are generated artifacts, not the source; use the markdown.

**D5 · Nothing in Part C is new strategy.** Every headline, stat and "so what" is drawn from dashboards already committed to this branch. If a figure here looks wrong, the dashboard is wrong too, and both should change together.
